# Feature: the learner confirms the generated knowledge map

Lane P1 (contract) with P2 (service), P3 (routes, live; their spec is `specs/graph-confirmation/` on `ptest2`), P5 (screen). Status: **contract aligned to P3's live routes on
2026-11-07** (P1's first draft used a different route and body; P3's design, identity from the session, is the better one).

## Why
The map is generated by a model from textbook chunks, and the demo labels it "Bản nháp tự động — chưa được giáo viên
duyệt". The learner should see the map they are about to be assessed on and accept it before practice. The backend refuses
practice, attempts and hints (409) until that acceptance exists, so the web needs one shared, unambiguous shape.

## The contract (`app/schemas.py`)
- `GET /graph/review?subject=` → `GraphReview {learner_id, subject, graph_revision, graph, confirmed}`. `graph` is the
  generated `KnowledgeGraph` (concepts and prerequisite edges, no mastery). `graph_revision` is the sha256 of the map as a
  64-character lower-case hex string, set by the backend; nobody parses it. `confirmed` is true only when this exact
  revision is already confirmed.
- `POST /graph/confirm` takes `GraphConfirm {subject, graph_revision}` and returns `GraphConfirmed {learner_id, subject,
  graph_revision, confirmed: true}`. The revision is **required**: there is no "confirm the latest". The body has **no learner
  id**; unknown keys are rejected.
- **Identity** is the learner session cookie `nodetrail_learner` (HttpOnly, SameSite=Lax, set when the learner is created).
  No cookie gives **401**. The browser cannot name a learner, and the shared API key is not a learner identity.
- Errors are HTTP codes, not models: **401** no session; **404** unknown learner or topic; **409** stale revision (the map
  changed since the learner saw it: fetch `GET /graph/review` again and show it); **422** invalid; **503** graph not ready.
- Until a learner has confirmed the current revision, `POST /attempts`, `POST /tutor/hint` and the practice routes return
  **409**. The same status means different things on different routes; the client tells them apart by route.

## Behaviour that must hold (P2's service)
1. Confirmation is **explicit**, a separate user action, never a side effect of reading the map.
2. The revision confirmed is the one the learner was shown: P5 keeps `graph_revision` from the same `GET /graph/review`
   response it displayed.
3. A change to the graph removes acceptance, including changing back to a previously accepted graph. Replaying an identical
   graph keeps it. Confirmation changes no mastery, item status, placement or job.

## Out of scope
Real login (after the contest); editing the map; a "reject" action (the learner leaves); the body of a 409 beyond a
Vietnamese `detail` string.

## Acceptance
- Contract tests in `tests/engine/test_contracts.py` and the mocks `graph-review.response`, `graph-confirm.*` pass.
- Through the real routes: confirm with the shown revision gives 200 and practice then works; an old revision gives 409;
  practice before confirming gives 409; a body that names a learner is rejected. Step 2a of `specs/contracts/h7-run-sheet.md`.
